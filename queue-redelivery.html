Delivery can repeat. The effect should not.

The broker tracks acknowledgment, not your database commit. Make the consumer safe to run again for the same logical operation.

What the ACK actually means

It tells the broker this delivery is handled. In this example, once the failed connection is detected and closed, the unacknowledged message returns to the queue.

A database commit and a broker ACK are separate actions. The application can fail between them.

What protection actually needs

A stable message ID, a database-enforced unique key scoped to this consumer, and one transaction that commits both the processed marker and the order write.

On redelivery, a committed marker means the effect already happened. Skip that effect and acknowledge the new delivery.

Show the transactional pattern →
On delivery of msg_1042:
  BEGIN TRANSACTION
    Atomically claim (consumer_name, message_id)
    using a UNIQUE constraint.

    If an already-committed claim exists:
      Do not repeat the order write.
    Otherwise:
      Insert the order in this same transaction.
  COMMIT

  ACK the current delivery on its own channel.

This is pseudocode, not a copy-paste implementation. Handle concurrent claims and uniqueness conflicts using your database’s transaction semantics. If the transaction fails, neither the marker nor the order should commit. Do not swallow an unrelated write failure and ACK it as a duplicate.

Why not acknowledge before writing?

If the broker accepts the ACK and the consumer then crashes before the write commits, the message is gone from this queue and the order is missing. Moving the ACK earlier trades duplicate risk for lost work.

What this example simplifies →

The illustration uses a surviving RabbitMQ-style queue with manual ACKs, an available database, and no external side effects. Actual failure detection takes time; redelivery can go to a different consumer. Recovery, ordering, delivery limits, and dead-letter behavior depend on configuration.

The processed marker protects only writes in its database transaction. Sending an email or calling a payment API needs its own safe delivery or idempotency strategy. The redelivered flag is a hint, not a durable business operation ID. Marker retention must cover the replay horizon; distinct message IDs for the same business operation may also require business-level uniqueness.
