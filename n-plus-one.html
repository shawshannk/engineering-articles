Your API makes 101 of them.

Fetch 100 orders. Then fetch each order’s customer separately. The screen looks fine. The database sees 1 + 100 queries. That’s the N+1 trap.

SAME SCREEN. FEWER ROUND TRIPS.

1 orders + 100 customers
AFTER · JOINED PROJECTION
1 query
Orders + customer names

Illustrative counts, not a benchmark. Before: one separate lookup per order. After: a simple relational join. Dots show up to 101 queries.

Fetch for the screen, not inside the loop.

Project the order fields and customer name together. Appropriate eager loading or batching can also avoid per-row calls.

Try this today: inspect database command logs for one list request. Repeated lookups with different IDs are a clue. Check the generated SQL before calling it fixed.

Show me the EF Core example →

This example assumes a required Order-to-Customer relationship and a relational provider. The first version explicitly performs a lookup per order, so it does not depend on lazy loading being enabled.

Before: the loop makes database calls

var orders = await db.Orders
    .OrderBy(o => o.Id)
    .Take(100)
    .ToListAsync();

foreach (var order in orders)
{
    var customerName = await db.Customers
        .Where(c => c.Id == order.CustomerId)
        .Select(c => c.Name)
        .SingleAsync();

    // Build the row using order.Id and customerName.
}

After: shape the result in the query

var rows = await db.Orders
    .OrderBy(o => o.Id)
    .Take(100)
    .Select(o => new
    {
        OrderId = o.Id,
        CustomerName = o.Customer.Name
    })
    .ToListAsync();

The projection can translate into one SQL statement joining orders to customers. It returns the fields this screen needs.

One thing to remember →

A navigation property does not always cause another query. Lazy loading, explicit lookups, and already-loaded data behave differently. Also, one huge join is not automatically best: collection joins can multiply rows, and split queries or batching may be a better tradeoff. Measure query count, payload size, and latency.
