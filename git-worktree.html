Git Version Control

The Git Feature Nobody Teaches

Git worktree has been in Git since 2.5 and most developers have never used it. Here is what it does and why you should care.

By Shashank 6 min read May 2026
01

The Problem

You are mid-feature. Files half staged, a mental model loaded, your editor has the right tabs open. Then a message arrives. There is a bug on main. Fix it now.

So you stash, switch branches, fix the bug, switch back, pop the stash, and spend ten minutes reconstructing what you were doing. Sometimes the stash pops with a conflict. Sometimes you forget to pop it at all. It is a friction tax you pay every single time.

Git worktree eliminates this. It lets you check out multiple branches simultaneously, each in its own directory, sharing a single .git database. Your original working directory stays untouched. You do the urgent work somewhere else, commit, push, clean up, and come back exactly where you left off.

02

How It Works

A normal clone is one directory, one branch at a time:

~/projects/my-repo/
  .git/        # full git database
  src/         # files from your current branch

After adding a worktree:

~/projects/my-repo/          # main worktree, feature/dashboard
  .git/                      # ONE shared git database
  src/

~/projects/bugfix-431/       # linked worktree, fix/431
  .git                       # a FILE, not a folder, points back
  src/                       # files from fix/431

The .git in the linked worktree is a plain text file with one line pointing back to the real database. Git tracks each worktree's own HEAD and staging area inside .git/worktrees/. Two directories, two branches, one repo. No duplication, no second clone.

Key insight

Staging changes in one worktree never affects another. Each worktree has its own index. But branches and objects are shared, so commits made in any worktree are immediately visible everywhere.

03

The Commands

Create a worktree

git worktree add ../bugfix-431 -b fix/431 origin/main
PartWhat it does
git worktree addCreates a linked worktree
../bugfix-431Path where the new directory gets created
-b fix/431Creates and checks out a new branch named fix/431
origin/mainStarting point for the new branch, equivalent to git branch fix/431 origin/main

If the branch already exists, drop -b and pass the name directly:

git worktree add ../bugfix-431 fix/431

List all open worktrees

git worktree list

# output
/home/user/my-repo          abc1234 [feature/dashboard]
/home/user/bugfix-431       def5678 [fix/431]

Remove a worktree

git worktree remove ../bugfix-431

Deletes the directory and its entry in .git/worktrees/. Refuses if there are uncommitted changes. Add --force to override.

Prune stale references

git worktree prune

If you deleted a worktree directory manually with rm -rf, Git still has a stale entry. This command cleans it up. Run it whenever git worktree list shows a path that no longer exists.

04

Rules Before You Use It

The same branch cannot be in two worktrees at once. Git enforces this. The error message is already checked out. It prevents you from editing the same branch in two places simultaneously.

Deleting a worktree does not delete the branch. git worktree remove only removes the directory and the registration. The branch still lives locally and on the remote. To clean up completely:

git worktree remove ../bugfix-431  # remove the directory
git branch -d fix/431              # delete local branch
git push origin --delete fix/431   # delete remote branch if needed

If the branch was never merged and Git refuses -d, use capital -D to force it:

git branch -D fix/431

New branches start local-only. Creating a branch via -b means it only exists on your machine. Push when ready:

git push -u origin fix/431

Stashes are per-repo, not per-worktree. A stash created in your main directory is visible from the linked worktree too. They share the same .git.

Git hooks apply to all worktrees. Pre-commit, pre-push, everything in .git/hooks/ runs wherever you commit.

Do not move a worktree after creating it. Git stores the absolute path. If you rename or move the directory, Git loses track. Run git worktree prune and recreate it at the new path.

If you create worktrees inside the repo root, add them to .gitignore. Otherwise Git treats them as untracked content:

echo "worktrees/" >> .gitignore
05

The Workflow in Practice

# you are on feature/dashboard, mid-work
cd ~/projects/my-repo

# bug reported, create a worktree for the fix
git worktree add ../bugfix-431 -b fix/431 origin/main

# open a second VS Code window pointed at the new directory
code ../bugfix-431

# fix the bug, commit, push
cd ../bugfix-431
git commit -am "fix: null ref in payment handler"
git push -u origin fix/431

# back to your feature, nothing has changed
cd ../my-repo

# clean up once the PR is merged
git worktree remove ../bugfix-431
git branch -d fix/431

Your feature/dashboard branch was never touched. The editor state in your first window is exactly as you left it. The second VS Code window ran independently in its own directory. That is the practical payoff.

06

Multiple Worktrees in Parallel

You are not limited to one. If a bug needs fixing on both dev and prod while you stay on your feature branch:

git worktree add ./worktrees/fix-dev  -b fix/bug-dev  origin/dev
git worktree add ./worktrees/fix-prod -b fix/bug-prod origin/main

# three directories live simultaneously
# my-repo/               feature/dashboard
# worktrees/fix-dev/     fix/bug-dev
# worktrees/fix-prod/    fix/bug-prod

Open three VS Code windows, one per directory. Work on all three independently without a single branch switch.

When not to use it

Worktrees solve one specific problem: you are deep in work on one branch and something urgent lands on another. They are not a replacement for branches and they do not help when a change needs to span two branches at once. The sweet spot is exactly what they were designed for: something urgent arrives, you handle it without dropping what you are doing, and you clean up when it is done.
