The browser asks for 100 orders. Why does the database receive 101 queries?

The N+1 pattern is one query for a list, followed by a separate query for each item. Follow the round trips, then change how the API retrieves the same fields.

Same response. Different work behind it.

For 100 orders, the separate-lookup example executes 1 order query plus 100 customer queries. The joined projection returns the order IDs and customer names in one statement. Both send one HTTP response containing 100 order rows.

Check whether query count grows with page size. Inspect database command logs for one request, then confirm the generated SQL and measure the changed endpoint.

EF Core example: make the round trips explicit

Illustrative excerpts, not compiled here. Assume a relational provider, a required order-to-customer relationship, stable data, and existing tenant authorization. tenantId is trusted server context, not an unchecked client parameter. Both versions select the same ordered page and fields.

Before: one query inside each iteration

var orders = await db.Orders
    .Where(o => o.TenantId == tenantId)
    .OrderBy(o => o.Id)
    .Take(pageSize)
    .Select(o => new { o.Id, o.CustomerId })
    .ToListAsync(cancellationToken);

foreach (var order in orders)
{
    var name = await db.Customers
        .Where(c => c.TenantId == tenantId && c.Id == order.CustomerId)
        .Select(c => c.Name)
        .SingleAsync(cancellationToken);
    // Add { OrderId = order.Id, CustomerName = name } to the response.
}

After: project the needed fields together

var rows = await db.Orders
    .Where(o => o.TenantId == tenantId)
    .OrderBy(o => o.Id)
    .Take(pageSize)
    .Select(o => new
    {
        OrderId = o.Id,
        CustomerName = o.Customer.Name
    })
    .ToListAsync(cancellationToken);

The model must enforce tenant-consistent relationships, and the actual query must preserve authorization. This simple reference projection is assumed to translate to one joined SQL statement. Inspect its SQL on your provider; more complex projections and collection loading can behave differently.

Assumptions and what the counters do not prove
  • The page has exactly the selected number of orders. Each order has one valid customer. Data does not change during the flow; no failure, retry, total-count query or extra authorization query is modeled.
  • The separate-lookup version deliberately performs one database query per order, even if customer IDs repeat. It has no caching, batching or identity-map shortcut.
  • One query counter increment means one executed database statement and round trip in this example. Visual batches do not represent SQL batching or concurrent execution.
  • Response rows are order-list rows, not total database rows scanned or transferred. The progress meter shows rows assembled before the HTTP response is sent.
  • A navigation property does not automatically issue SQL. Lazy loading, explicit loading and already-loaded data differ.
  • One statement is not a universal performance guarantee. Check query plans, indexes, payload size and latency. Collection joins can multiply rows; batching or split queries can be appropriate.
  • These reads are not shown inside a transaction. Real consistency requirements under concurrent writes may affect your choice of isolation and query strategy.
Try this with your team

Compare 10 and 100 orders under both strategies. If your endpoint shows similar growth, locate the repeated statement before adding a cache. Confirm both implementations return the required fields and preserve access rules.
