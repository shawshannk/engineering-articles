Why D is the strongest plan

Keep the payment pending while you establish its actual state. A known gateway reference can help with lookup. A supported retry with the same valid key lets the gateway recognize the original operation.

If the first request completed, recover its result. If it never arrived, the retry can execute it. If it is still running, follow the gateway’s in-progress response and retry policy.

What must exist before the timeout

  • Persist an operation key before sending the original request.
  • Send that key to the gateway, not just your own API.
  • Reuse the same key and parameters for that operation’s retries.
  • Prevent concurrent checkout requests from creating separate attempts for the same order.
Why isn’t a status check alone enough?

Checking status is useful. But “not found” may mean the original request is delayed or has not become visible yet. A fresh-key retry can race with it. Use authoritative gateway state, safe retry semantics, and ongoing reconciliation rather than treating one empty lookup as proof of failure.

What if the original request had no idempotency key?

You cannot add a key afterward and expect it to deduplicate an earlier unkeyed request. Keep the outcome unresolved, use available gateway references, and reconcile through the provider’s supported mechanisms. Do not blindly start another charge.

Does the same key guarantee success forever?

No. Keys have provider-specific retention and scope. Changed parameters may be rejected, concurrent requests may need to wait, and a stored error may be replayed. Check the provider’s contract. If the key has expired or the outcome remains uncertain, reconcile before issuing a new operation.

What would production recovery add?

Bounded retries with backoff and jitter, verified and deduplicated webhook handling, durable payment state, and scheduled reconciliation. Fulfil the order only after an authoritative successful payment state. This diagram simplifies those mechanisms to explain the decision.
