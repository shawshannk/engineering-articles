AI-written code still needs evidence.

The agent finished your feature. What would make you comfortable reviewing it?

By Shashank · 8 min read · October 2026

Looks finishedDefine the contractRead the evidenceChoose the checksHand it over
01 / The convincing summary

A feature that looks finished

You ask a coding agent to add customerReference to an order response. It changes a DTO and an endpoint, then reports:

“Implementation complete. All changes verified.”

The diff looks tidy. Then someone calls the endpoint with an older order and discovers that the field is missing. The agent assumed that a nullable C# property would always appear as a JSON field. The application actually omits null values.

This is an invented example, but the review problem is concrete: the completion summary told you the intended outcome without showing the observed outcome. A reviewer still has to connect the requirement to the code and to a check that could have caught the mistake.

Evidence is an inspectable observation tied to a specific change, environment, and expected result. A build log, a meaningful assertion, an HTTP response, or a reviewed diff can supply it. Each answers a different question. None proves that every possible defect is absent.

The central lesson: verification effort should follow the consequences of being wrong. A three-line authorization change can need more scrutiny than a large documentation edit.

AI makes producing a plausible implementation faster. That is useful. It also makes it easier to reach the review stage before anyone has decided what “works” means. Keep that decision explicit.

02 / One change, a clear boundary

Define the contract before checking the code

For this example, assume an ASP.NET Core API using System.Text.Json and an existing relational database column. An internal order already has an optional customer reference. We are exposing that value in GET /orders/{id}; we are not changing how orders are created or persisted.

The agreed response contract is camelCase JSON, with customerReference always present. It is a string when supplied and JSON null otherwise. Existing fields retain their meaning. Access remains restricted to the order’s tenant. Identifiers below are synthetic.

Reference supplied

{
  "id": "order-demo-42",
  "status": "pending",
  "customerReference": "PO-DEMO-17"
}

Older order

{
  "id": "order-demo-41",
  "status": "pending",
  "customerReference": null
}

That gives us observable acceptance criteria: the populated value survives the query and mapping; the empty case has the agreed shape; existing response fields are unchanged; and the tenant boundary still holds.

Adding a response field is compatible only for consumers that tolerate unknown properties. A strict validator, generated client, or snapshot comparison may reject it. Check the known consumer contract instead of calling every additive change “non-breaking.” If the database column does not exist, this is a larger change with migration and deployment questions.

A C# implementation detail worth verifying

System.Text.Json can omit null properties when DefaultIgnoreCondition is WhenWritingNull. A property-level Never condition can retain this field. This excerpt assumes the contract above, not a universal API convention.

using System.Text.Json.Serialization;

public sealed record OrderResponse(
    string Id,
    string Status,
    [property: JsonIgnore(Condition = JsonIgnoreCondition.Never)]
    string? CustomerReference);

// In the existing tenant-filtered query/projection:
// new OrderResponse(order.Id, order.Status, order.CustomerReference)

Declaring the property does not prove the endpoint populates it. Inspect the actual projection and execute the response checks using the application’s serializer settings. These snippets are illustrative; they have not been compiled against a runnable sample application.

Supply the agent with the endpoint, current DTO, mapping, serializer setup, relevant tests, and repository instructions. Ask it to inspect nearby behavior before changing it. Too little context encourages guesses; an entire unrelated codebase can bury the constraint that matters.

03 / Claims need a scope

Read “verified” as a question

Start with the final diff. Does the change reach the actual response path? Did it alter a shared serializer setting to fix one field? Did it remove a tenant filter, weaken an assertion, or touch unrelated files? A passing test is less persuasive if the same change quietly removed the behavior the test used to protect.

Then connect each check to a failure it could detect. “The test suite passed” is incomplete until you know which suite, whether tests were discovered, and whether the changed path was exercised. An exit code of zero can describe a successful command that tested nothing relevant.

These are complementary checks, not a mandatory staircase for every task. A local UI label needs different evidence from an invoice calculation. Choose the smallest set that addresses the plausible failures, then widen it when the results or diff reveal more risk.

A contract assertion that can catch the empty-field bug

In an existing xUnit integration fixture, seed an order without a reference, make an authorized request, assert the HTTP result, and inspect the JSON field. This excerpt starts after that fixture has returned a JsonElement named body:

Assert.True(body.TryGetProperty("customerReference", out var reference));
Assert.Equal(JsonValueKind.Null, reference.ValueKind);

// In a separate populated-order case:
Assert.Equal("PO-DEMO-17",
    populatedBody.GetProperty("customerReference").GetString());

A check that only deserializes into a DTO with a nullable property may accept both missing and explicit-null fields. Assert the distinction the contract requires. Also check existing fields and cross-tenant access with the established authorization fixture.

ASP.NET Core’s WebApplicationFactory supports testing requests against a configured test host. Inspect its database substitutions: an in-memory fake can check HTTP behavior while leaving production-provider query behavior untested. Choose a representative provider when the query itself is the risk.

Tests written by the agent need review too. Ask whether an assertion would fail for a plausible broken implementation, such as returning null for every order. A test that checks only “status is 200” cannot establish that the new value survives mapping.

Keep evidence attached to the version it checked. Record the commit SHA, configuration, and relevant fixture assumptions. After a later edit, rerun the affected checks. A log from yesterday’s code is background information, not proof about today’s diff.

04 / Proportional verification

Choose checks by consequence

For our response-field example, moderate effort is reasonable if the value already exists, consumers are known, and authorization stays unchanged. Escalate if the diff changes a shared setting, persistence, sensitive data exposure, or access rules. File count is a poor risk score.

Verification has costs: slow suites, unreliable fixtures, and setup time. Reducing those costs means selecting checks with a reason, not dropping the checks that would detect the important failure. If a required environment is unavailable, record the gap and make the next owner’s action clear.

Make a verification plan

Planning aid only. Ticks record your own review notes; this page runs no build or tests. Nothing persists after refresh.

What kind of change are you reviewing?

Written plans for all three risk levels
  • Low: for a local text or presentation change, inspect the diff and check the affected behavior. Record the result and any gap.
  • Moderate: for the API example, add a build, populated and null contract cases, and checks of existing fields, known consumers and tenant access.
  • High: for security, money, schema or concurrency changes, add representative integration checks, failure cases, and a rollout/recovery review where relevant.

These are starting points. A “low” label does not excuse a missing check when the actual diff exposes more risk.

05 / Make the next review easier

A handoff someone can inspect

A useful handoff links the requirement, changed path, result, and remaining uncertainty. It should help a reviewer decide where to spend attention. A giant terminal dump without interpretation can hide the same gap as a confident one-line summary.

Compare two handoffs for the same task

Both handoffs below are fictional. Commands, filenames, counts, and results illustrate the format; they were not executed for an API project here.

Hard to review

Added customerReference. All tests pass. Fully verified and ready to merge.

No command, checked version, acceptance mapping, or remaining gap.

Evidence attached

Changed: OrderResponse.cs, order query projection, and OrderResponseTests.cs. Existing stored value now appears in the response, including explicit null.

Checked version: the PR commit linked in CI; Release configuration.

Ran: dotnet build --configuration Release, exit 0. dotnet test --configuration Release --filter FullyQualifiedName~OrderResponseTests, exit 0; 4 discovered, 4 passed.

Covered: populated value, explicit null, existing fields, cross-tenant denial. Test-host database was replaced with a fixture.

Gap: production-provider query and strict-client compatibility not exercised. Review those before release.

Do not replace “not run” with “should pass.” Record failed checks too, including whether the failure is in the implementation or the environment. If a suite is blocked, name the blocked criterion and the exact follow-up. “Integration tests unavailable because the database fixture could not start” is useful; “everything else looks good” is not a substitute.

When the agent can execute commands, ask for the actual results and accessible logs or CI links. When it cannot, ask it to prepare runnable checks and state that limitation. The author’s summary is a pointer to evidence; the reviewer should be able to inspect the evidence itself.

Reusable task and evidence handoff template
Task: [one observable change]
Context: [endpoint, data path, conventions, repository instructions]
Assumptions: [provider, consumers, authorization, deployment constraints]
Acceptance criteria: [observable success and failure cases]

Implement the smallest change that satisfies these criteria.
Inspect the final diff and relevant test assertions.
Run appropriate checks available in this environment.
Report actual results; do not infer a pass from an unrun command.

Handoff:
- What changed, why, and which files are involved
- Checked commit/configuration and fixture assumptions
- Criterion -> check -> actual result -> evidence location
- Commands run, exit codes, tests discovered/passed/failed/skipped
- Checks not run, why, and the next action
- Remaining risks and what a human should review

Human review still matters after the checks pass. Look at the business rule, whether the test asserts the intended contract, and what the test environment substitutes. For sensitive changes, include someone who understands the relevant domain. More polished generated prose does not reduce the cost of getting those rules wrong.

For your next AI-generated PR, pick one acceptance criterion and follow it all the way to an actual result.

If you cannot find that path, the change may be implemented, but its handoff is incomplete. Ask for the missing evidence before treating it as review-ready.
