A refresh token is used twice.

Two tabs try to refresh one session. One succeeds. The other sends the old token. Should that end the session?

A refresh token lets a client request new access tokens. With rotation, a successful refresh replaces it. Reusing the old value is where policy matters.

The outcome depends on policy

Tab A exchanges R1 for R2. Under the strict scenario, a second R1 request revokes the refresh-token family. Under the modeled Auth0-style interval, a +1-second reuse issues R3; a +8-second reuse revokes the family. An early thief gets the same overlap treatment as Tab B.

A reuse interval reduces some false alarms. It also creates a replay window. Coordinate refreshes in the client, and check your provider’s exact behavior.

Assumptions and provider-specific limits
  • This is a deterministic teaching simulation, not an authentication implementation. Tokens are labels, not credentials. No network calls occur.
  • Both requests target one tracked token family. Tab A reaches the server first; its response arrives before the second request. In-flight response reordering and additional refreshes are outside this flow.
  • The server serializes token checks and family updates atomically across instances. A process-local lock alone would not establish this assumption.
  • Strict mode models rotation with reuse detection and no overlap. The grant is revoked when an already-consumed refresh token is presented.
  • Auth0-style mode models its documented reuse interval: the most recently superseded token can be exchanged again during the interval, issuing another replacement. After R3 is issued, R1 is too old; it cannot keep being reused merely because five seconds have not elapsed. This does not claim that R2 was revoked by issuing R3.
  • The window is illustrated as five seconds after the first exchange. We do not simulate the precise boundary instant. Providers and configurations differ.
  • These are bearer tokens, without sender constraint. Client identity and short timing do not prove that the sender is legitimate.
What about access tokens and the two tabs?

The ledger tracks refresh tokens only. Already-issued access tokens may remain usable until expiry if APIs validate them locally without a revocation check. A refresh failure therefore does not necessarily mean every API call fails immediately.

After strict reuse detection, the client needs a new authorization flow to obtain a usable refresh grant. That does not necessarily force a password prompt if an identity-provider session still exists.

For legitimate concurrency, centralize refresh coordination using your supported SDK or a suitable session owner. A promise shared in one tab does not coordinate all tabs. Avoid logging token values; observe refresh failures and confirm recovery behavior against your actual provider.
